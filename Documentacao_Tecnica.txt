================================================================================
1. DESCRIÇÃO DO PROBLEMA
================================================================================

Lojas de carros enfrentam desafios significativos no gerenciamento de estoque:

• Dificuldade em rastrear veículos disponíveis em tempo real
• Falta de visibilidade sobre rotatividade de estoque
• Análise manual de preços e tendências de mercado
• Ausência de KPIs consolidados para tomada de decisão
• Processos manuais propensos a erros

Este projeto aborda esses problemas através de um sistema automatizado de 
análise de dados que integra ingestão, processamento, armazenamento e 
visualização de informações de estoque.

================================================================================
2. OBJETIVOS DO SISTEMA E JUSTIFICATIVA TÉCNICA
================================================================================

2.1 OBJETIVOS
-------------
• Automatizar a coleta e processamento de dados de estoque
• Fornecer KPIs em tempo real para gestão de estoque
• Implementar pipeline escalável de dados
• Criar dashboards interativos para análise
• Estabelecer arquitetura de Data Lake com camadas Bronze/Silver/Gold

2.2 JUSTIFICATIVA TÉCNICA
--------------------------
A arquitetura escolhida permite processamento tanto em tempo real (streaming) 
quanto batch, garantindo flexibilidade e escalabilidade. O uso de Data Lake 
com camadas permite rastreabilidade completa dos dados desde a origem até os 
KPIs finais.

4. ARQUITETURA COMPLETA DO PIPELINE
================================================================================

O sistema implementa uma arquitetura moderna de Data Lake com processamento 
em múltiplas camadas.

4.1 COMPONENTES PRINCIPAIS
---------------------------

CAMADA DE INGESTÃO
• Apache Kafka: Streaming de dados em tempo real
  - Tópicos: car_inventory, car_sales
  - Producer/Consumer para processamento contínuo
• Apache Airflow: Processamento batch agendado

CAMADA DE PROCESSAMENTO
• Apache Spark: Processamento distribuído
  - Transformações de dados
  - Agregações e cálculos de KPIs
• Pandas: Processamento local para análises exploratórias

CAMADA DE ARMAZENAMENTO (DATA LAKE)
• MinIO (S3-compatible):
  - Bronze: Dados brutos em JSON
  - Silver: Dados limpos e estruturados em Parquet
  - Gold: Dados agregados e KPIs em Parquet
• PostgreSQL: Dados relacionais para Metabase

CAMADA DE VISUALIZAÇÃO
• Metabase: Dashboards e relatórios interativos
• FastAPI: API REST com documentação automática

4.2 FLUXO DE DADOS
------------------
1. Dados fonte → Kafka Producer
2. Kafka Consumer → MinIO (Bronze Layer)
3. Spark Processing → Limpeza e transformação
4. MinIO (Silver Layer) → Dados estruturados
5. Spark Aggregation → Cálculo de KPIs
6. MinIO (Gold Layer) → Dados analíticos
7. API + Metabase → Visualização

6. DECISÕES TÉCNICAS E TRADE-OFFS
================================================================================

6.1 KAFKA VS RABBITMQ
---------------------
Decisão: Apache Kafka
Justificativa: Melhor para streaming de alto volume, persistência de mensagens, 
replay de eventos
Trade-off: Maior complexidade de configuração

6.2 MINIO VS HDFS
-----------------
Decisão: MinIO
Justificativa: Compatibilidade S3, mais leve, fácil de containerizar
Trade-off: Menos recursos para clusters massivos

6.3 METABASE VS GRAFANA
------------------------
Decisão: Metabase
Justificativa: Interface mais amigável, melhor para análise de negócio
Trade-off: Menos customizável que Grafana

6.4 FORMATO PARQUET VS CSV
---------------------------
Decisão: Parquet para Silver/Gold
Justificativa: Compressão eficiente, leitura colunar, melhor performance
Trade-off: Não é human-readable

6.5 DOCKER COMPOSE VS KUBERNETES
---------------------------------
Decisão: Docker Compose
Justificativa: Simplicidade para ambiente de desenvolvimento/demonstração
Trade-off: Não é adequado para produção em larga escala

7. GUIA DE EXECUÇÃO - COMO RODAR DO ZERO
================================================================================

7.1 PRÉ-REQUISITOS
------------------
• Docker Desktop instalado e rodando
• Python 3.8 ou superior
• Git (opcional)
• Mínimo 8GB RAM disponível
• 20GB de espaço em disco

7.2 PASSO A PASSO
-----------------

PASSO 1: Clonar/Baixar o projeto
    cd ProvaGustavo

PASSO 2: Instalar dependências Python
    cd src
    pip install -r requirements.txt

PASSO 3: Subir infraestrutura Docker
    cd ../infra
    docker-compose up -d

PASSO 4: Aguardar inicialização (2-3 minutos)
    docker-compose ps

PASSO 5: Gerar dados de exemplo
    cd ../datasets
    python sample_data.py

PASSO 6: Executar pipeline
    cd ../src
    python main.py

PASSO 7: Acessar serviços
    • MinIO: http://localhost:9001 (admin/password123)
    • Metabase: http://localhost:3000
    • API: http://localhost:8000/docs

7.3 COMANDOS ÚTEIS
------------------
# Ver logs dos containers
docker-compose logs -f

# Parar todos os serviços
docker-compose down

# Reiniciar um serviço específico
docker-compose restart metabase

# Limpar volumes (CUIDADO: apaga dados)
docker-compose down -v

10. KPIs IMPLEMENTADOS
================================================================================

10.1 KPIs DE ESTOQUE
--------------------
• Total de Veículos: Quantidade total no estoque
• Valor Total do Estoque: Soma dos preços de todos os veículos
• Preço Médio: Preço médio dos veículos em estoque
• Taxa de Disponibilidade: % de veículos disponíveis para venda
• Idade Média da Frota: Idade média dos veículos em anos

10.2 KPIs DE VENDAS
-------------------
• Total de Vendas: Número total de vendas realizadas
• Receita Total: Valor total das vendas
• Ticket Médio: Valor médio por venda
• Taxa de Conversão: % de veículos vendidos vs. estoque total
• Tempo Médio de Venda: Dias entre entrada e venda

10.3 ANÁLISES DISPONÍVEIS
--------------------------
• Estoque por marca e modelo
• Vendas por período
• Distribuição de preços
• Rotatividade por categoria
• Performance por vendedor
• Análise de margem de lucro

10.4 ENDPOINTS DA API
---------------------
• GET /kpis - KPIs principais
• GET /inventory/by-brand - Estoque por marca
• GET /inventory/available - Veículos disponíveis
• GET /sales/summary - Resumo de vendas
• GET /analytics/price-distribution - Distribuição de preços

Exemplo de resposta:
{
  "total_veiculos": 1000,
  "valor_total_estoque": 45000000.00,
  "preco_medio": 45000.00,
  "veiculos_disponiveis": 600,
  "marcas_ativas": 7,
  "idade_media_frota": 2.3
}

11. PONTOS DE FALHA E LIMITAÇÕES
================================================================================

11.1 PONTOS DE FALHA
--------------------
• Kafka: Se o broker cair, streaming para
• MinIO: Perda de dados se volumes não persistidos
• Spark: Falhas em processamento de grandes volumes
• Docker: Recursos insuficientes podem derrubar containers
• Rede: Comunicação entre containers pode falhar
• PostgreSQL: Single point of failure sem replicação

11.2 LIMITAÇÕES
---------------
• Escalabilidade: Docker Compose não é para produção
• Segurança: Senhas hardcoded, sem SSL/TLS
• Monitoramento: Ausência de logs centralizados
• Backup: Sem estratégia de backup automatizado
• Alta Disponibilidade: Single point of failure
• Performance: Dados sintéticos, não testado em escala real
• Integração: Não conecta com sistemas externos
• Autenticação: Sem controle de acesso granular
• Validação: Validação básica de dados

11.3 MELHORIAS FUTURAS
----------------------

13. TROUBLESHOOTING
================================================================================

PROBLEMA: Porta já em uso
--------------------------
Solução:
    netstat -ano | findstr :9000
    taskkill /PID <PID> /F

PROBLEMA: Containers não sobem
-------------------------------
Solução:
    docker-compose logs
    docker-compose down
    docker-compose up -d --force-recreate

PROBLEMA: Dados não aparecem
-----------------------------
Solução:
1. Verificar se os dados foram gerados: dir datasets\
2. Executar pipeline novamente: python src\main.py
3. Verificar logs do MinIO

PROBLEMA: Memória insuficiente
-------------------------------
Solução:
1. Aumentar memória do Docker Desktop (Settings > Resources)
2. Reduzir número de workers do Spark
3. Processar dados em lotes menores
